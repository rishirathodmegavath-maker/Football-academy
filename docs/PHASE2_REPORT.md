## 2. What was implemented

### WP1: hosting and server foundation

- Node pinned: `.node-version` 24.13.0, `engines` `>=24.13.0 <25`. `tsx` moved from dev to runtime dependencies because the background worker is a TypeScript script (lockfile regenerated; `--frozen-lockfile` install verified).
- `scripts/preflight.mjs` (`start`, `--build`, `--artifact`): Node version, HTTPS origin, secret strength, absolute storage outside the app directory, file/directory permissions (POSIX), QA flags, proxy settings, email consistency, backup settings, and the headers baked into the build. Prints verdicts only; never a secret.
- `GET /api/health` (liveness, no dependencies) and `GET /api/ready` (database opens, schema present, not draining; reveals nothing).
- Clean shutdown (`src/instrumentation.ts`, `src/server/shutdown.ts`): marks the service draining on SIGTERM/SIGINT, checkpoints the SQLite log and closes on exit.
- `deploy/`: systemd units (web, worker, backup service and timer, sandboxed, `UMask=0077`, preflight as `ExecStartPre`), `release.sh` (preflight → verified pre-deploy backup → atomic symlink switch → restart → readiness wait → **automatic rollback** → prune), `rollback.sh`, `sportozen.env.example`.
- Finding fixed in docs: a production build loads the authentication module, which refuses an HTTPS origin without a secret and opens a database. Builds need a throw-away secret and database path (preflight `--build` now checks both).
- Docs: `docs/DEPLOYMENT.md`.

### WP2: proxy, forwarded headers, URL configuration

- `deploy/nginx` (+ Caddy alternative): TLS, redirect, ACME path, unknown hosts dropped, `X-Forwarded-For`/`X-Real-IP` **overwritten**, `Forwarded` removed, `/api/ready` local-only, edge limits, 2 MB body cap, `server_tokens off`.
- `src/server/proxy-config.ts` + `auth.ts`: Better Auth's client-address resolution is configured explicitly (`SPORTOZEN_TRUSTED_PROXIES`, `SPORTOZEN_CLIENT_IP_HEADER`); invalid values stop start-up instead of being ignored.
- Existing behaviour confirmed: the mutation origin check compares the browser `Origin` to `BETTER_AUTH_URL`, independent of `Host`.

### WP3: database and persistence

- SQLite retained; PostgreSQL not started (porting estimate and triggers in `docs/DATABASE_OPERATIONS.md`).
- Verified in a fresh process: `journal_mode=wal`, `busy_timeout=5000`, `foreign_keys=1`, `recursive_triggers=1`, `integrity_check=ok`.
- Persistence verified: a process killed with SIGKILL right after a commit loses nothing; a process started in a different working directory sees the data; opening again is a no-op.
- File permissions: directory 0700, file 0600 (verified on Linux), preflight enforces.
- **Defect fixed:** migration 003 checked for a missing column and then altered the table outside any lock; two processes starting together on an old database could crash the second with "duplicate column name". It now runs under `BEGIN IMMEDIATE` and tolerates the column already existing. Proved deterministically (the old code fails the new test with exactly that error).
- Operator script `platform-admin.mjs` now sets `busy_timeout` and `recursive_triggers`.
- Docs: `docs/DATABASE_OPERATIONS.md` (settings, migration list and safe procedure, recovery decision tree, limits).

### WP4: backup and disaster recovery

`scripts/lib/backup.mjs` + three commands (`backup-database.mjs`, `backup-status.mjs`, `restore-database.mjs`), Node built-ins only.

- Consistent online snapshot (`VACUUM INTO` on a read-only connection), `integrity_check`, row counts per table, gzip, AES-256-GCM encryption (refused unencrypted), then a **full restore of the backup into a scratch file and comparison of hash, integrity, schema version and every table's row count** before it is stored.
- Off-server: a mounted-directory target (copy verified by hash) or a command target (JSON argv, no shell, output redacted). Provider-independent by design.
- Retention (hourly/daily/monthly counts, pre-deploy protection, always the newest), pruning only after success and only files matching the backup name pattern.
- Restore writes a **new** file only after verification; refuses the live database, an existing file and relative paths; `--rehearse` restores into a temporary directory, times it and deletes it.
- RPO/RTO are configuration (`SPORTOZEN_BACKUP_RPO_MINUTES/RTO_MINUTES`), empty until approved; `backup-status` exits 3 while no RPO is set.
- Docs: `docs/BACKUP_AND_RECOVERY.md` (cut-over procedure, options for RPO/RTO, checklist).

### WP5: email

- `email_outbox` (migration 009, additive), outbox processing in the web process and the worker (atomic claim, lease recovery), retry schedule 1 min → 6 h, permanent vs transient failures, expiry before send, per-address hourly cap, erasure of the secret link once a message is finished, 90-day purge.

- UI: sign-in screen (forgot password, confirmation notices), new `/reset-password` screen, one status line on the two existing invite forms. They reuse existing components and styles; unchanged while features are off. See the UI-lock note in Section 6.
- Logs contain only ids, purposes, attempt numbers and codes; verified by capturing every console call across success, retry and failure.

## 5. Architecture and configuration decisions (made, with reasons)

1. **One server, SQLite, loopback app behind nginx.** Matches the data layer and the assessment; PostgreSQL deferred as instructed.
2. **Preflight as a gate**, run by systemd (`ExecStartPre`) and the release script, so unsafe configuration cannot start.
3. **Release by symlink with automatic rollback, and a verified pre-deploy backup that aborts the release if it fails.** Migrations are additive and not reverted; rollback is code-only.
4. **Backups by `VACUUM INTO`, not the incremental backup API**, because the latter restarts whenever another connection writes and may never finish on a busy database. Measured about 50 ms for the snapshot under a continuous writer.
5. **Backups are verified by restoring them**, encrypted by default, restored only to new files.
6. **Storage provider independence** (mounted directory or command), because the store is an owner decision.
7. **Email everything off by default; start-up refuses inconsistent settings;** the outbox keeps no secret link after sending; the web request never waits for the provider (no timing leak about accounts).
8. **Verification does not auto-sign-in**; reset revokes all sessions; invitation links never auto-accept.
9. **UI kept minimal** under the UI lock: reused components, no new layouts, a pending-invitations screen deliberately not built.
10. **Test infrastructure, not product code, absorbed the load problem:** many new tests start real processes. The Vitest configuration now caps workers at 8 and sets a 15-second test limit, and the heavy files have explicit 30-second limits. Measured: tests of 0.3 s alone reached 5.7–7 s when the whole suite ran at once. Earlier full runs failed about half the time before the change and 0 of 8 after.

Also measured and fixed in my own tests: a backup test that took 21 s because it committed 2,000 rows one at a time (an fsync each) now takes 0.4 s.

## 3. Messaging repair report

**Reported:** Batch Announcements dialog is visible, clicking Send does nothing.

**What the workflow is:** Save draft → Send announcement for approval → (Owner/Admin) Preview, tick the review box, Approve → optionally Queue for WhatsApp. Idempotency keys (UUID plus content digest) prevent duplicates on retry; the client keeps one in-flight request; versions stop overwrites; coaches may draft and submit but only Owner/Admin may approve.

**Reproduction (before):** Owner opens Messages → Batch announcements, chooses a batch, types text. Every request returned 200, but after each click the confirmation, and after "Approve" the 409 "No eligible recipients can be approved", appeared at the top of the scrolling form while the cursor was on the footer buttons: outside the viewport. Evidence: `evidence/announce-repro/`.

**Second defect found while verifying persistence and delivery:** even when the click worked, nobody could ever see the message. The only recipient path was WhatsApp (disabled until a provider is configured), and approval was refused unless a guardian had verified WhatsApp consent. A guardian logged into the app saw nothing.

**Repair:**

1. Feedback region above the buttons: success text per step, the server's error text, and the reason the next button is unavailable ("Choose at least one batch", "You have unsaved changes", "Waiting for an owner or admin to approve", "Tick the review box…").
2. `GET /api/workspaces/{academy}/announcements` (guardians only). Returns approved or queued, unexpired announcements for batches that contain one of the guardian's own children: generic body, kind, urgency, times and those batch names. Nothing about other children or guardians, contacts, reviewers, fingerprints or delivery state. Read live: a link added later shows it, a link removed hides it. Editing withdraws it; cancel and expiry hide it.
3. Approval needs at least one linked guardian (the preview reports "N guardians will read this in the app"). The WhatsApp fingerprint, consent checks, blockers and Queue step are unchanged.
4. Guardian Home and Messages show an "Academy announcements" card. It is fetched every time the screen opens (it is treated as sensitive, so a cancelled announcement cannot linger in memory) and shows an error note instead of failing silently.
5. Not changed: quiet hours, consent, template and sender rules for WhatsApp; the generic-content privacy rules; approval history and audit.

**Verified (browser, production build, WhatsApp off):** the coach drafts and submits and is told an owner must approve; the owner saves, submits, previews, approves; guardian A (child in the batch) sees the text on Home and Messages; guardian B (child in another batch) sees nothing and the page source does not contain the text; the owner's own call to the guardian route is refused (403); approving a batch with no linked guardian shows the error in view; cancelling removes it from guardian A; the message region is inside the viewport at 1366 and 390 px. Evidence: `tests/e2e/announcement-delivery.spec.ts`, `evidence/announce-after/`.

**Other messaging workflows checked:** the private parent–coach conversation (create, reply both ways, staff-only note hidden from the parent, a stranger refused, closed conversation refuses replies with 409, empty body 400): 8/8 checks passed by API. Existing browser specs for communication, periods, parent updates and publication passed in the full run (section 7). WhatsApp reply and send flows are provider-blocked.

## 4. Performance

Method: production build (`next start`), the synthetic 60-player academy copy, Chromium via Playwright, same machine for before and after. "Mobile profile": 390×844, 4× CPU slowdown, 1.6 Mbps down / 150 ms RTT (the Lighthouse "slow 4G" profile), median of 3 runs. Raw data: `evidence/perf-*.json`.

### 4.1 Baseline findings

- **Localhost desktop is already fast**: first paint ~130 ms, largest paint ~280–330 ms, 1–3 API calls per page, in-app navigation 65–95 ms. Page weight 299 KB of script in 12 files.
- **APIs are fast**: every read p50 2–30 ms (owner home summary 27 ms, owner full workspace 52 ms, report list 30 ms); throughput with 20 concurrent clients about 280 reads/s and 170 writes/s with p95 under 140 ms; sign-in 110–130 ms.
- **The weak spot is the mobile-class load.** 914 KB–1.1 MB per page, of which 562 KB was the two fonts; text invisible until they arrived.
- **Database:** growing communication tables were scanned (section 4.3).

**The one failure, understood.** `academy-portal.spec.ts` asserted that every `Portal Noto` font face in `document.fonts` has status `loaded`. After the font change each weight has a Latin face (loaded) and a full-range face that the browser loads only when a character outside Latin appears, so it correctly stays `unloaded`. The product behaved as designed; the assertion described the old delivery. It now requires, per weight, a loaded face and no face in `error`. This is the same spec that failed once in an earlier phase for a different reason (a run across midnight); the two causes are unrelated.

**Skipped tests, all intentional (platform conditions, not disabled tests):** `deploy-scripts.test.ts` (whole file, bash scripts), one test in `preflight.test.ts` and two in `ops-review-fixes.test.ts` are skipped on Windows (`skipIf(win32)`). ## 8. Security and operational findings

**Security and data integrity**

- Access control: the new route is guardian-only. The security matrix (anonymous 401, stranger 403, other-academy owner 403, paused academy 403, revoked member 403, no-store headers, no internals in refusals) now covers it, plus a role test (owner, admin, coach, support refused) and a tenant test (same user id in another academy sees nothing).
- The guardian response contains only fields listed above; a test searches the JSON for contacts, author and reviewer ids, the approval object, fingerprints and child names.
- Strict CSP is enforced (nonce plus `strict-dynamic`, `font-src 'self'`); no console errors, warnings, CSP reports or failed requests on 16 owner and parent pages; the only dynamic-code mention in the source is a comment about zod; no HTML-injection sinks.
- F5 closes a validation gap: stored data that later makes a document fail.
- Data integrity checker: no findings on three databases.
- The Owner/Coach/Parent/Platform-Admin permission regression passes (matrix, membership lifecycle, platform tests, announcements, finance, reports).
- Optimisations did not touch authorisation: the font and index changes are delivery and storage only; no cache was added to financial, attendance, permission or announcement data. The guardian card is explicitly re-fetched on every open.

**Operational**

- Client read timeout (F6) and the communication indexes (F4) are the operational changes.
- Worker cadence is every 10 s; the email outbox is purged hourly, the delivery tables are not (O2).
- WP8 monitoring: reviewed, not changed. Its documented open items are repeated in O8 for a separate decision.
- A stale server on a reused port served an old build during my own measurements; the final measurements and the regression use freshly started servers.
